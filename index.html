0. ひとことで言うと

「大きなキャリーケースを持った旅行者でも、伊豆大島を気持ちよく回れる1泊2日プランを、
バスのデータ（GTFS）とAIで自動で作るサービス」

1. なぜやるの？（3つの理由）

🧳

困っている人がいる

フェリーで大島に着いた観光客は、大きなキャリーケースを持ったまま動くのが大変。人気の三原山（山登り）にはすぐ行けない。
📊

データで決めたい

「なんとなく」ではなく、GTFS（バスの時刻表デジタルデータ）とAIを使って、正確でムダのない旅程を作る。
🚀

未来の観光を提案したい

東京都知事杯ODHで「これからの観光モデル」を提案する。
🚨 新しくわかった「本当に困る」証拠 ✅ 確認済み
大島バスの手荷物ルール：無料で持ち込めるのは3辺合計1m以内・10kgまで。それを超えるキャリーケースは1個500円の有料、しかも混んでいると乗車を断られることがある。
→ 「荷物を持って三原山に行く」のはお金も手間もリスクもある、という一次ソースです。（出典：大島バス 手荷物規定PDF）

2. だれの・どんな困りごとを解決する？（エレベーターピッチ）

😥 困っている人伊豆大島に来た、キャリーケースなど大きな荷物を持った観光客
↓
🧱 困りごと荷物を持ったままだと三原山などにすぐ行けない・不便・バスに乗れないかも
↓
💡 私たちの答え「GTFS活用 スマートモデルコース」
↓
😊 うれしいこと1日目は荷物を持ったままでも楽しめる「椿・花ガーデン」、2日目はホテルに荷物を預けて「三原山」を満喫 → ムダがなく、ストレスのない旅
🤔 ふつうの乗換案内アプリと何がちがう？
乗換案内は「A→Bに一番早く行く方法」しか教えてくれません。私たちのサービスは「この船で着く」「荷物がある」「2日ある」という条件の中で、実際にできる旅程を組み立てて、バスの時刻表でちゃんと成立するか検証してから出すところが新しい点です。

4. やらないこと（スコープ外）

❌ やらない理由
1日目に三原山へ行くキャリーケースを持っての登山は現実的でない。バスも有料・乗車拒否リスク
道案内・翻訳だけのガイドスマホやAIで代わりができる。もっと深い文化体験・知的好奇心を満たすガイドに注力
ログイン、予約機能、多言語、リアルタイム運行情報、全路線対応ハッカソン期間では作りきれない。1コースを完璧に見せる方が勝てる

5. ⚠️ 今いちばん心配なこと（課題①②③）

ここがクリアできないと、1日目のルートを作り直す必要があります。

課題今の状況リスクどうする？
① 昼ごはんの場所椿・花ガーデンのカフェ・ショップは「リニューアルで休業中」の可能性大。近くに歩いて行ける飲食店も未確認観光客が「お昼ごはん難民」になる東京・竹芝や船内でお弁当を買って持ち込む
② 飲食物の持ち込みOK？園内に芝生の大広場があることはわかっている。でも「持ち込みOKか」「そこで食べていいか」は ❓未確認持ち込みNGだと①の作戦がくずれる椿・花ガーデンに電話で公式ルールを確認（最優先）
③ 2時間20分は長い？短い？バス時刻から逆算すると滞在は10:28〜12:48時間が足りない or 余りすぎる8/22の現地検証で実際に歩いて計測。ダメなら代替スポットで再構成
🛟 代替スポットも1つ用意しておく（例：波浮港や元町の屋内施設）。もし椿・花ガーデンがNGでも旅程がくずれないように。

8. 💻 PoC/RPをどう作るか

✅ 最小機能（これだけ作る）

入力3つ：到着港（元町／岡田／未定）・到着時刻（ジェット船9:35 / 10:00プリセット）・キャリーケース有無。宿泊は大島温泉ホテル固定。
出力：1泊2日タイムライン＋スポット詳細。

🧱 技術構成

Cloudflare Pages ＋ 素のHTML/JS（DB不要）。GTFSは事前にスクリプトで抽出→静的JSONで同梱（数十KB）。AI説明文は Pages Functions 1本（/api/explain）。AIが失敗してもテンプレ文で動く＝AIなしでもデモ成立。

📱 画面（3つだけ）

① 入力（港・到着時刻・キャリー有無トグル）
② タイムライン（バス便カード・警告バッジ・運賃合計・2日目タブ）
③ スポット詳細（写真・所要・荷物適性・次発3本）

データの流れ

GTFS zip（ODPT）
  → scripts/build_gtfs.py：8/22・23に有効な service_id を解決、対象バス停の trip だけ抽出
  → data/timetable.json（{tripId, serviceId, routeName, stops:[{stopId, dep, arr}]}）
  → ブラウザで「バス停A→Bで、時刻T以降の最初の便」を探す（便数が少ないので単純な探索でOK）

荷物あり/なしで分かれるルール表

スポット荷物なし荷物あり理由
椿・花ガーデン○ 10:28着で観光＋弁当○（園内平坦）港から8分・300円
三原山山頂口（初日）○× 未舗装、バス500円有料・乗車拒否リスク2日目に預けてから
大島温泉ホテル15:00 IN12:58着で荷物預け → 温泉・周辺散策（午後の上り便なし）三原山温泉バス停直結
元町散策○△坂道

実装：各スポットに luggageScore(0〜2) を持たせ、荷物ありなら score≥1 だけ候補に残し、バス時刻順に詰める。バス手荷物500円／混雑時拒否リスクはタイムライン上に警告バッジで表示。

デモシナリオ（審査員に見せる順番）

  1. 荷物なし → 初日に山頂まで行く案が出る
  2. 同じ条件でキャリーONに切替 → 椿・花ガーデン → 12:48便でホテル先着・預け → 翌朝三原山、と旅程が組み替わる
  3. 到着港を岡田に切替 → 時刻が追従する
  4. 「説明文を生成」ボタン → AIの文章が出る

現地チェックリスト（8/22–23）

  • 当日の入港地とアプリの港切替が一致するか
  • 10:20便が実在し、椿・花ガーデン10:28着か（遅れの幅を記録）
  • キャリーケースのバス持込可否・500円徴収・混雑度
  • 椿・花ガーデンで荷物を置ける場所があるか／弁当を食べられる場所
  • ホテル12:58着でチェックイン前に荷物を預けられるか
  • 山頂口〜遊歩道でキャリーが本当に困難か（写真を撮る）
  • 港・園内・山頂の電波状況（オフライン動作が必要か）

リスクと代替案

  • ODPTトークン取得が遅れる → 公式PDFから起こした手入力JSONで開発を止めない（三原山ラインの主要便は既に抽出済み）
  • 8月と9月でダイヤが変わる → ピッチ日は8月ダイヤに固定
  • 港が当日変わる → 「入港地」という抽象バス停を用意して実港にマッピング
  • バスで荷物拒否 → 「港のコインロッカー／ホテル直行」ルートを常に第2案として表示

コード断片（次のバスを探す関数）

// バス停from→toで、時刻t(HH:MM)以降の最初の便を返す
export function nextBus(tt, from, to, t) {
  const m = s => { const [h, mi] = s.split(":").map(Number); return h*60+mi; };
  return tt.flatMap(trip => {
    const i = trip.stops.findIndex(s => s.stopId === from);
    const j = trip.stops.findIndex(s => s.stopId === to);
    return (i >= 0 && j > i && m(trip.stops[i].dep) >= m(t))
      ? [{ trip, dep: trip.stops[i].dep, arr: trip.stops[j].arr }] : [];
  }).sort((a, b) => m(a.dep) - m(b.dep))[0] ?? null;
}

10. 📚 用語ミニ辞典

GTFS / GTFS-JP
バスや電車の時刻表・路線・停留所をコンピュータが読める形にした共通データ形式。JPは日本版
オープンデータ
誰でも自由に使っていいと公開されているデータ。行政が公開していることが多い
ODH
東京都知事杯オープンデータ・ハッカソン。都のオープンデータでサービスを作って競う大会
ODPT
公共交通オープンデータセンター。大島バスのGTFSはここで公開されている
PoC
Proof of Concept。「このアイデアは本当に動くのか」を確かめるための試作
RP
Rapid Prototype。短期間でざっくり作る試作品
MVP
Minimum Viable Product。最小限の機能だけ持った、使える製品
Cloudflare Pages
ウェブサイトを無料で公開できるサービス。今回の開発環境
service_id
GTFSの中で「この便はどの曜日・季節に走るか」を表すID（例：三原山＿夏＿3）
ペルソナ
サービスを使う代表的な人物像。「初めて大島に来た、知り合いのいない、キャリーケースを持った観光客」
QOL
Quality of Life。生活の質。ここでは「休暇の質」
ピッチ
短時間で審査員に企画を売り込むプレゼン
一次情報
自分で現地に行って確かめた情報。伝聞よりずっと強い
